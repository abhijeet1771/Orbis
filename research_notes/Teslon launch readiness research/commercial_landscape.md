## 1. Test impact and test intelligence platforms

### Takeaway
Every test-impact platform found decides "what to run" from runtime data (per-test coverage recorded by agents: SeaLights, Teamscale, Parasoft, Datadog, Harness, Drill4J, Azure TIA), from ML on history (Develocity, Appsurify, BrowserStack, Smart Tests in its original form) or, newly, from LLM semantic similarity (CloudBees Smart Tests, 2026). None reads code statically to name screens or features, and only four claim manual-tester support (SeaLights, Teamscale, Parasoft CTP, Drill4J), all by instrumenting a running test environment while testers click. The output unit is "tests" (existing test cases), not "areas of the app".

### Inferences
- [Inf] Datadog has the only precisely stated skip rule (identical covered files + tracked files since a passing run). That is a real, checkable guarantee, but only relative to coverage that was recorded, and it explicitly loses fidelity with child processes, forks and suite hooks. Teslon's claim "never a wrong skip" will be compared with this rule.
- [Inf] ML/history selectors (Develocity, Appsurify, BrowserStack, Smart Tests) give statistical confidence ("profiles", "% of failures caught"), never a per-item proof. Develocity's own docs push it to post-merge/nightly, which is an implicit admission that per-PR skipping is risky.
- [Inf] Manual-test support always means "instrument the app under test and have testers start/stop a session" (Parasoft CTP), or "browser extension + backend agents" (Drill4J, SeaLights). That is the instrumentation burden Teslon avoids, and also the evidence Teslon lacks: these tools see what was actually executed, Teslon only infers it.
- [Inf] Consolidation: SeaLights went to Tricentis (2024-07), Launchable to CloudBees (2024-08). Test impact is being folded into big suites (Tricentis, CloudBees, Datadog, Harness, Gradle) rather than sold standalone. A standalone Teslon competes against "a checkbox in a tool we already pay for".
- [Inf] The market's output is a list of TESTS (needs an existing suite). Teslon's output is a list of AREAS with checks (works with no suite at all, which is common for manual QA). This is the sharpest true difference.

## 2. AI pull-request reviewers and agents that write test plans or impact sections

### Takeaway
AI PR reviewers are the best-funded adjacent category (CodeRabbit $1.5B valuation Aug 2026; Cursor bought Graphite Dec 2025) and they now market "blast radius" and change explanation, but none makes a verifiable "safe to skip" claim. Their testing guidance is LLM text (summaries, suggested or generated unit tests), measured accuracy on bug-finding is 40-65% F1 at best with 4-46% false-positive rates depending on who ran the test, and peer-reviewed evidence shows AI-written PR descriptions often claim work that was never done. They are the thing a buyer already has and will compare Teslon with first.

### Inferences
- [Inf] These tools describe the code change for developers; Teslon describes the app change for testers. But CodeRabbit's "Triage / blast radius" (Aug 2026) and Graphite+Bugbot inside Cursor show the reviewers are moving toward impact. A "QA impact" section is a prompt away for them; the defensible gap is determinism and verification (no LLM in decisions, re-read citations, proven skips), not the idea.
- [Inf] Their accuracy numbers are on bug-finding, not on "what to test", and no vendor publishes any measurement of test-scoping accuracy. Teslon can be the first to publish a recall/false-skip number, which is a differentiator only if measured on real third-party repos.
- [Inf] The MSR '26 data is useful sales evidence: LLM text about PRs is wrong in a measurable fraction of cases, and test PRs are the worst. But Teslon should not over-claim from it: 1.7% high inconsistency overall is lower than many critics imply.

## 3. AI QA products: does any decide regression scope from a diff?

### Takeaway

## 9. White space: proof-backed static "safe to skip" at screen or feature level

### Takeaway
I found no commercial or open-source product that gives a per-item, machine-checked "safe to skip" at screen, API or feature level from static reading of two commits, without instrumenting a running app. Every skip claim in the market is either relative to recorded coverage (Datadog's identical-files rule; SeaLights/Teamscale/Parasoft/Harness), statistical (Develocity profiles; Launchable "90% confidence with 10-20% of tests"), or an LLM's judgement with a fall-back to run everything (Momentic "if not safe, run full set"). The space is open, but it is open for reasons that are also Teslon's biggest risks.

### Cited Findings
- Closest neighbours, each missing one of (static, area-level, proven skip, for testers): Momentic AI Select (static import index + LLM, its own tests, alpha, no proof) — [Momentic docs](https://momentic.ai/docs/ai/select); LiveCompare (static SAP object graph + production usage, SAP only, "most-at-risk" not "proven safe") — [LiveCompare docs](https://docs.tricentis.com/livecompare-2026.1/content/templates/impact%20analysis/smart_impact_analysis.htm); Datadog TIA (precise skip rule, but needs per-test coverage from prior runs) — [Datadog docs](https://docs.datadoghq.com/tests/test_impact_analysis/how_it_works/); Playwright `--only-changed` (import-based, its own docs call it a heuristic, from PRIOR-ART) ; naeemdadi/impact-analysis OSS (import graph → routes, LLM phrases scenarios, no skip proofs, from PRIOR-ART); Moderne data tables (cross-repo endpoint/usages, no QA output) — [Moderne blog](https://moderne.io/blog/source-code-impact-analysis-with-data-tables).
- Research on static regression test selection: FSE 2016 (Legunsen et al.) found class-level static RTS (STARTS) comparable with dynamic RTS (Ekstazi) with "few safety violations"; OOPSLA 2019 "Reflection-Aware Static RTS" found reflection was the only cause of unsafety observed, and reflection-aware variants improved safety at high cost (1,173 versions of 24 Java projects); purely static variants stayed safe in their experiments but lost precision; a hybrid can still be unsafe with test-order dependencies; ASE 2022 journal-first comparison: STARTS and Ekstazi did not differ on safety violations, Ekstazi had fewer precision violations. [I: peer-reviewed; 2016-2022, partly STALE?] — [Legunsen et al. FSE 2016 PDF](https://mir.cs.illinois.edu/~marinov/publications/LegunsenETAL16StaticRTS.pdf); [OOPSLA 2019 Reflection-Aware Static RTS](https://2019.splashcon.org/details/splash-2019-oopsla/68/Reflection-Aware-Static-Regression-Test-Selection); [ASE 2022 empirical comparison of four Java RTS techniques](https://conf.researchr.org/details/ase-2022/ase-2022-journal-first-papers/18/An-empirical-comparison-of-four-Java-based-regression-test-selection-techniques)
- Vendors' own documented blind spots of runtime approaches (library dependencies, compiler options, external services, data files, child processes) — [Datadog TIA troubleshooting](https://docs.datadoghq.com/tests/test_impact_analysis/troubleshooting/); [Datadog TIA how it works](https://docs.datadoghq.com/tests/test_impact_analysis/how_it_works/)

### Inferences (why the space is empty)
- [Inf] Soundness is hard and liability is real. Static analysis of Spring/Angular apps meets reflection, dependency injection, AOP, config-driven wiring, feature flags, dynamic routes and cross-service contracts. The RTS literature shows reflection alone breaks static safety unless handled at significant cost. A vendor that promises "never a wrong skip" owns every escaped defect; incumbents prefer statistical confidence plus "run a defensive full suite" advice (Launchable) or post-merge use (Develocity).
- [Inf] Runtime coverage is language-agnostic and sells as "truth" (what actually ran). Static, framework-aware modelling must be built per framework and per version, which is expensive and why Teslon reads only Java/Spring, Angular, Vue and a few build/migration formats.
- [Inf] Budget follows CI cost. Most TIA products are sold on CI-minutes saved for automated suites (developer tooling budgets), not on manual-QA hours saved; the manual-QA scoping buyer is less visible and less served (only SeaLights, Teamscale, Parasoft, Drill4J, all instrumented).
- [Inf] LLMs made "good-enough" impact text nearly free (CodeRabbit, Copilot, QA.tech, home-made "QA impact report" bots), which lowers willingness to pay for rigour unless the buyer has been burned by a wrong skip.
- [Inf] Therefore Teslon's open space is narrow but real: tester-facing, area-level, deterministic, offline, with proofs and an explicit "unclear" state. To own it, Teslon must prove the false-skip rate on third-party code and keep "unclear" small enough to be useful. A static tool that says "unclear" on most PRs is safe but not valuable (PRIOR-ART's first scan: 19 of 20 PRs not modelled).

### Gaps
- No published false-skip rate exists for any commercial tool, so there is no market benchmark to beat; Teslon would set it.
- GitHub Marketplace not searched exhaustively for small "PR impact" apps; small OSS projects beyond PRIOR-ART not re-surveyed here.

### How a buyer will compare Teslon
- An enterprise test manager on Tricentis will compare it with SeaLights + qTest (and Release Risk Intelligence when it ships): "we already have change-to-test mapping".
- A dev-led team will compare it with the AI reviewer it already pays for (CodeRabbit, Copilot, Bugbot): "our bot already writes a summary and a test plan".
- A team without QA staff will compare it with QA.tech / Momentic / Meticulous: "an agent actually clicks through the app on each PR".
- An SAP or Salesforce shop will compare it with LiveCompare / Panaya / Copado and ask for the same outputs: impacted / not impacted / most-at-risk, hits vs test gaps, by functional area.
- A platform team will compare it with Datadog TIA or Develocity and ask for the skip rule in one sentence.

### The five hardest questions a buyer will ask
1. "What is your measured false-skip rate on code you did not write, judged by something independent of you?" Today the answer is: own fixtures, mutants, two open-source apps, 55 PRs on own fixture repos; never a real team's code, never real QA users (team brief). Incumbents also lack independent numbers, but they have years of customers; Teslon has none. The minimum credible answer is a third-party benchmark (e.g., runtime coverage per page as an oracle, as PRIOR-ART proposed) on several real repos, with escapes counted.
2. "What do I get on the PRs you cannot read?" Everything outside Java/Spring + Angular/Vue + Maven/npm is held "unclear". Datadog, SeaLights and Harness cover many more languages because coverage is language-agnostic. The buyer will ask for the share of their PRs that come back mostly "unclear" and what the team should do then; PRIOR-ART's first scan had 19 of 20 PRs not modelled (since improved, per the brief, but the real-world ratio is unmeasured).
3. "Why trust static inference over recorded execution?" SeaLights, Teamscale, Parasoft, Datadog and Meticulous see what actually ran, including reflection, DI wiring, config and feature flags; the RTS literature shows reflection is the classic cause of static unsafety. Teslon must show, case by case, how its proofs handle those mechanisms, and how it handles Datadog's documented blind spots (dependency bumps, config, data files, external services).
4. "How does this plug into how my testers already work?" Test leads live in Xray, Zephyr, TestRail, qTest or Azure Test Plans and think in test cases, not areas. LiveCompare's "hits vs test gaps" is the bar: map each area to existing test cases and show uncovered areas. Without that, Teslon is one more PR comment for testers who often do not read PRs.
5. "Why pay for this instead of a prompt in the AI reviewer we already have, or a checkbox in the suite we already license?" The honest answer is determinism, offline operation, evidence that is re-checked, and a skip claim that is either proven or withheld; versus LLM text shown by MSR '26 to contain phantom claims and by benchmarks to have 4-46% false positives on bug-finding. That answer only wins if Teslon publishes accuracy data that none of the LLM tools publish, and prices near the $8-24 per committer/developer reference points.

### Inferences
- [Inf] The strongest positioning, supported by this survey: "the only static, offline, proof-or-unclear PR impact report for testers", not "the most accurate tool" (unproven) and not "AI-free test selection" (Datadog's and Teamscale's selection is not AI either).
- [Inf] The most dangerous competitor is not a startup but a bundle: Tricentis (SeaLights + LiveCompare + qTest + Tabnine context + Release Risk Intelligence) for enterprises, and CodeRabbit/Cursor/GitHub for dev-led teams.
- [Inf] To earn "1 of 1", Teslon needs, in order: an independent false-skip benchmark on real repos; a measured "unclear" ratio on real repos; test-management integration ("hits vs gaps"); then stack breadth (React, Kotlin, Gradle first, by market share in Java/TS enterprises).
