## Q1. Theory: undecidability, soundness vs completeness vs precision, soundiness, and how "sound" tools word their guarantee

### Takeaway
No static tool can decide "this PR cannot change what area X does" for all programs (Rice's theorem), so "100% accurate" in the sense of "never a wrong skip AND never a needless test" is impossible in principle; what is possible is ONE-SIDED: a tool can be sound (never a wrong skip) relative to a written list of assumptions, at the cost of holding some areas as unclear. Every tool that claims soundness (Astree, Frama-C Eva, CompCert) states its guarantee as "relative to a model and stated hypotheses"; every large whole-program analyzer for Java/JS is "soundy" (deliberately unsound on named features). Teslon's honest claim must therefore be "sound relative to assumptions A1..An, and every skip shows which ones it used", not "100%".

### Cited Findings
- Rice's theorem (1953): every non-trivial semantic property of programs is undecidable. "Does commit B change the observable behaviour of area X relative to commit A?" is a non-trivial semantic property (it is program equivalence restricted to a slice), so no algorithm decides it exactly for all programs; any total, terminating analyzer must err on one side (miss impact = unsound, or flag non-impact = incomplete/imprecise). [Mem; textbook result, e.g. Rice, Trans. AMS 74 (1953)]
- Terminology used in the field: a "sound" may-analysis over-approximates all executions (no false negatives for the property checked); "complete" means no false alarms; "precision" is how close the over-approximation is to the truth. For Teslon: SKIP = "no execution of area X can observe the change"; sound = no wrong skip; precision = how few areas are needlessly TEST/UNCLEAR. [Mem]
- "In Defense of Soundiness: A Manifesto", Livshits, Sridharan, Smaragdakis, Lhotak, Amaral, Chang, Guyer, Khedker, Moller, Vardoulakis, CACM 58(2):44-46, Feb 2015: the authors "are not aware of a single realistic whole-program analysis tool that does not purposely make unsound choices"; they coin "soundy" for analyses that over-approximate most features but deliberately under-approximate a recognised subset (Java reflection, JS eval, native code, dynamic loading); their call to action is that papers and tools must DOCUMENT exactly which features are handled unsoundly. — [CACM full text](https://cacm.acm.org/magazines/2015/2/182650-in-defense-of-soundiness/fulltext); [author PDF](https://www.doc.ic.ac.uk/~livshits/papers/pdf/cacm15.pdf) [S for the quote and definition; co-author list Mem]
- Astree (ENS/AbsInt): a runtime-error analysis "is called sound if it never omits to signal an error that can appear in some execution environment"; when the environment is restricted, "restrictions are hypotheses for the static analyzer which must be validated by some other means" (e.g. configuration file with maximal execution time and input ranges); "the analysis results are correct only if these assumptions are correct" (Kastner et al., ERTS2 2010); results "describe correctly all executions before the first runtime error, if any". — [Astree site](https://www.astree.ens.fr/); [Kastner et al. ERTS 2010](https://www.di.ens.fr/~rival/papers/erts10.pdf) [S]
- Frama-C Eva: aims to prove absence of runtime errors caused by C undefined behaviours and "is able to report all errors that might happen — in the class of undefined behaviors supported by the analysis"; emits false alarms by design; NIST IR 8304 (SATE VI, 2020) found Astree and Frama-C/Eva satisfied the "Ockham Sound Analysis Criteria" on Juliet 1.3. — [frama-c.com](https://frama-c.com/); [NIST IR 8304 (2020)](https://nvlpubs.nist.gov/nistpubs/ir/2020/NIST.IR.8304.pdf) [S]. Note the NIST result is empirical evidence on a test suite, not a proof.
- CompCert (Leroy, CACM 2009): proves a semantic-preservation theorem (composed of per-pass proofs) from CompCert C ASTs to Asm ASTs, covering observable behaviours (termination, divergence, going wrong); the compiler may refuse to produce code. — [Leroy, CACM 2009](https://xavierleroy.org/publi/compcert-CACM.pdf); [CompCert manual](https://compcert.org/man/manual001.html) [S]. The trusted base (Coq kernel, the formal C semantics as specification, the unverified parser/assembler/linker, extraction to OCaml) is [Mem]. Lesson for Teslon: even the gold standard states WHAT is proven (preservation of semantics as formalised) and allows "refuse" as a correct outcome; Teslon's UNCLEAR plays the role of CompCert's refusal.
- Coverity, "A Few Billion Lines of Code Later" (Bessey et al., CACM 53(2), Feb 2010): "Like the PREfix product, we were also unsound. Our product did not verify the absence of errors but rather tried to find as many real bugs as possible"; they ignored constructs causing false positives or complexity (assembly, whole functions or files). — [CACM](https://cacm.acm.org/research/a-few-billion-lines-of-code-later); [PDF copy](https://web.eecs.umich.edu/~ryanph/jhu/cs624/spring21/readings/bloc-coverity.pdf) [S]. Lesson: the commercial default is unsound bug-finding; a "safe to skip" product inverts the requirement (a false negative is the costly error), which is rarer and harder.
- Infer: built on over-approximate separation logic; O'Hearn's Incorrectness Logic (POPL 2020) is the under-approximate dual, used by Pulse/Pulse-X (OOPSLA 2022) to report bugs with "no false positives (under certain assumptions)"; with an incomplete solver Pulse-X may still produce false positives. — [Le et al. OOPSLA 2022 PDF](https://people.mpi-sws.org/%7Edreyer/papers/finding-real-bugs/paper.pdf); [O'Hearn keynote slides](https://www.sos-vo.org/system/files/sos_files/Keynote_Underapproximate_Reasoning_at_Scale.pdf) [S]. Lesson: there are two honest one-sided guarantees, over-approximate ("no missed impact") and under-approximate ("every reported impact is real"); Teslon's SKIP needs the first; its TEST list is neither (it is over-approximate, so some TEST entries are not real impact).

### Inferences
- "Will it be 100% without mistakes?" The answer is no in the two-sided sense, and that is a theorem, not an engineering gap. The achievable target is one-sided and conditional: "zero wrong skips relative to the assumptions printed on each skip, provided the readers produced complete facts". The two conditions (assumptions hold; facts are complete) are exactly where real-world misses come from (see Q2).
- Teslon's existing assumption list (CERTIFICATE-2026-11-05.md, "Assumptions the checker prints") is the right shape, Astree-style. But several items are not hypotheses about the environment; they are deliberate under-approximations of the language/framework (e.g. "Jackson and JPA touch a data type only through its fields, accessors, constructors and lifecycle callbacks"; "Settings under logging, management, info and springdoc change nothing a user sees"). In soundiness terms those are the "recognised unsound subset" and should be labelled as such, separately from environment hypotheses (profile, deployed config) which a customer can validate. [inference from /home/user/teslon/research/CERTIFICATE-2026-11-05.md, section "Assumptions the checker prints"]
- The "content / relies" split (CERTIFICATE doc, step 5) means about 43% of real impact in Teslon's own truth tests is NOT re-derived by the checker. Under the soundness definitions above, the certificate is sound only for the "runs code" part; for the content part the guarantee rests on the engine alone. Any public claim must say this.

## Q2. Measured unsoundness of call graphs (Java, Android, JavaScript/TypeScript) and which dynamic features cause the misses

### Takeaway
Every published measurement finds that mature static call-graph builders miss real runtime edges: about 12% of runtime-observed methods/edges for Java in practice (median recall 0.884, 31 programs), 61% of executed methods on average for Android with 13 tools, and about 24% of edges for Node.js before Jelly's approximate interpretation (12% after). The misses cluster in a known list: reflection, dynamic proxies, serialization callbacks, dynamic class loading/ServiceLoader, invokedynamic/lambdas, native code, framework entry points and library callbacks into application code. These are exactly the mechanisms Spring and Angular/Vue are built on, so a source-level, rule-based reader like Teslon's should be assumed to have at least this class of gap until measured.

### Cited Findings
- Sui, Dietrich, Tahir, Fourtounis, "On the Recall of Static Call Graph Construction in Practice", ICSE 2020, pp. 1049-1060: 31 real-world Java programs; dynamic oracle from built-in and synthesised high-coverage tests; median recall 0.884; built-in tests expose dynamic behaviour better than generated tests; adding precision (context sensitivity) had little effect on recall, so "precision and recall appear to be separate concerns"; better support for dynamic language features would noticeably improve recall. — [ICSE 2020 page](https://2020.icse-conferences.org/details/icse-2020-papers/47/On-the-Recall-of-Static-Call-Graph-Construction-in-Practice); [artifact, Zenodo](https://zenodo.org/records/3672128) [S]
- Sui, Dietrich, Emery, Rasheed, Tahir, "On the Soundness of Call Graph Construction in the Presence of Dynamic Language Features: A Benchmark and Tool Evaluation", APLAS 2018 (LNCS, pp. 69-88): 34-program micro-benchmark in six categories (reflection, serialization, Unsafe, dynamic proxies, dynamic class loading, invokedynamic/JNI); none of Soot, WALA, Doop produced a sound call graph for every program. — [Springer DOI 10.1007/978-3-030-02768-1_4 via unpaywall](https://unpaywall.org/10.1007%2F978-3-030-02768-1_4); [BenchWork 2018 talk](https://2018.ecoop.org/event/benchwork-2018-talks-a-micro-benchmark-for-dynamic-program-behaviour) [S]
- Reif, Kubler, Eichberg, Helm, Mezini, "Judge: Identifying, Understanding, and Evaluating Sources of Unsoundness in Call Graphs", ISSTA 2019, pp. 251-261: capability profiles for Soot, WALA, Doop, OPAL; soundness-relevant language features and APIs are "used frequently" in modern bytecode; support for them "differs vastly", so comparing call graphs built by the same named algorithm (e.g. RTA) in different frameworks is meaningless. — [ISSTA 2019 page](https://conf.researchr.org/details/issta-2019/issta-2019-Technical-Papers/24/Judge-Identifying-Understanding-and-Evaluating-Sources-of-Unsoundness-in-Call-Grap) [S]
- Helm, Roth, Keidel, Reif, Mezini, "Unimocg" (ISSTA 2024): WALA and Soot fail to soundly analyse about half of the test cases across several call-graph algorithms, and "none of these algorithms are sound in the mathematical sense". — [OPAL PDF](https://opal-project.de/articles/Unimocg@ISSTA24.pdf) [S]
- Helm, Keidel, Kampkotter, Dusing, Roth, Hermann, Mezini, "Total Recall? How Good Are Static Call Graphs Really?", ISSTA 2024 (DOI 10.1145/3650212.3652114): eight call-graph implementations in four frameworks on four real Java programs; dynamic baselines built from the SAME fixed entry points with manual extension and coverage-guided fuzzing, because an unrestricted high-coverage baseline misstates recall. Numerical results not visible in snippets. — [ISSTA 2024 page](https://2024.issta.org/details/issta-2024-papers/10/Total-Recall-How-Good-Are-Static-Call-Graphs-Really-) [S; numbers = gap]
- Samhi, Just, Bissyande, Ernst, Klein, "Call Graph Soundness in Android Static Analysis", ISSTA 2024, pp. 945-957: 13 static tools vs dynamic analysis on 1,000 apps; on average the tools "failed to capture 61% of the dynamically-executed methods"; "a high level of precision in call graph construction is a synonym for a high level of unsoundness"; no existing approach, including mechanism-specific ones such as DroidRA for reflection, significantly improves soundness; slides: all tools miss at least 35% of entry points, and entry points are about 20% of all missed methods. — [author PDF](https://homes.cs.washington.edu/~mernst/pubs/callgraph-soundness-issta2024.pdf); [slides](https://homes.cs.washington.edu/~mernst/pubs/callgraph-soundness-issta2024-slides.pdf) [S; slide figures Sec]

- Santos, Mirakhorli, Shokri, "Seneca: Taint-Based Call Graph Construction for Java Object Deserialization", OOPSLA 2024 (arXiv 2311.00943, 2023): existing algorithms miss the callbacks invoked during (de)serialization; Seneca combines taint analysis and API modelling to make them sound for that feature. — [OOPSLA 2024 page](https://2024.splashcon.org/details/splash-2024-oopsla/41/Seneca-Taint-Based-Call-Graph-Construction-for-Java-Object-Deserialization) [S]
- Ali and Lhotak, "Application-only Call Graph Construction", ECOOP 2012 (LNCS 7313, pp. 688-712), and "Averroes: Whole-Program Analysis without the Whole Program", ECOOP 2013: ignoring library code and its callbacks into the application makes application call graphs unsound; under the "separate compilation assumption" (the library was compiled without knowledge of the application, so it can only call application code through overridden library-visible methods and reflection), a sound application-only call graph can be built with a generated library placeholder. — [ECOOP 2012 PDF](https://cormack.uwaterloo.ca/~olhotak/pubs/ecoop12.pdf); [ECOOP 2013 PDF](https://plg.uwaterloo.ca/~olhotak/pubs/ecoop13.pdf) [S]
- JavaScript: Feldthaus, Schafer, Sridharan, Dolby, Tip, "Efficient Construction of Approximate Call Graphs for JavaScript IDE Services", ICSE 2013: field-based flow analysis, "unsound in principle", precision at least 66% and recall at least 85% against dynamic call graphs; a 2014 CWI replication found deviations up to about 25% in precision and 11% in recall, and edge-based recall around 87-91%. — [ICSE 2013 page](https://2013.icse-conferences.org/content/efficient-construction-approximate-call-graphs-javascript-ide-services.html); [CWI replication](https://ir.cwi.nl/pub/23111) [S]
- Laursen, Xu, Moller, "Reducing Static Analysis Unsoundness with Approximate Interpretation", PLDI 2024 (PACMPL 8, art. 194): Jelly's pre-analysis executes code fragments to produce hints; on 36 Node.js projects with dynamic call graphs, average recall rose from 75.9% to 88.1% "with a negligible reduction in precision"; Jelly can measure its own recall against NodeProf dynamic call graphs. — [paper page](https://cs.au.dk/~amoeller/papers/approx); [Jelly on GitHub](https://www.github.com/cs-au-dk/jelly) [S]

### Inferences
- The best published Java and JS call-graph builders reach roughly 88% recall on real programs. Teslon's Java facts come from "a tokenizer and parsers, not a compiler" (CERTIFICATE doc, "Assumptions the checker prints"; its "Honest limits" call this level L3). Nothing in the literature suggests a source-level rule-based reader can beat bytecode-level points-to frameworks on recall; Teslon's protection is not better recall but turning known gaps into UNCLEAR. That protection works only for gaps it KNOWS about (reflection, unmatched HTTP calls, unknown topics). The literature's lesson is that the unknown-unknowns (an unmodelled framework callback, a proxy, a library callback) are silent by nature.
- Teslon's printed "dangling call" rate (7.3% to 18.0% in its own runs; CERTIFICATE doc, precision table) is a useful, honest unsoundness proxy, analogous to Judge's capability profile. It should be reported on every customer run, with a threshold above which skips are disabled.
- Its fallback of widening an unresolved call to "every method of that name the caller can see" is name-based resolution, similar in spirit to Feldthaus et al.'s field-based approach for JS: it improves recall but is still unsound when the callee is reached without a syntactic call (callbacks from Spring, Jackson, Hibernate, a logger's toString, Angular lifecycle hooks, Vue watchers).
- Teslon's own gauntlet oracle lists "library calls back into app code (toString from a logger)" and "reflection" as blind spots (GAUNTLET doc, "Honest limits"). The Ali-Lhotak separate-compilation assumption gives a cheap, sound rule for the first: any application method that overrides or implements a library-visible method (toString, equals, hashCode, compareTo, run, call, accept, Jackson-visible getters, Spring callback interfaces) is a potential entry point from any library call that receives that object. Teslon should treat such methods as reachable from every area that passes the object to library code, or record an unknown.
- The Android result (precision tuning increases unsoundness) is a warning for Teslon's history of "finer" checker rules (CERTIFICATE doc, third set of fixes). Each refinement that certifies more screens (security matchers, navigation guards, store returns) is a new soundness obligation and must come with its own mutation family.

## Q3. Framework modelling for Spring / Java EE, and build-time outputs as ground-truth facts

### Takeaway
Research frameworks only recently started modelling enterprise frameworks (JackEE on Doop, PLDI 2020; Jasmine on Soot, ASE 2022), and both report that without such models conventional call graphs miss most of an enterprise app (JackEE: more than 4x higher completeness on average than the most precise conventional analysis). Industrial tools (CodeQL, Semgrep) model Spring as hand-written source/sink/summary libraries for security, not as a sound bean graph. The strongest available move for Teslon is to stop re-implementing Spring and Angular/Vue semantics with rules and instead read facts the frameworks' own compilers emit: Spring AOT generated bean definitions, javac/SCIP symbol tables, Angular ngtsc type-check blocks, Vue language-core virtual code. Each of these is exact for ONE build configuration and states its own limits; none is a whole-program soundness proof, but each turns an L3 guess into an L0/L1 fact.

### Inferences
What each build-time source would prove for Teslon (my assessment):

| Source | What it gives | Exactness | What it does NOT cover | Cost to Teslon's design |
|---|---|---|---|---|
| javac symbols (SCIP-java, or javac + javap like Teslon's own gauntlet oracle) | resolved types, overloads, generics, every static call target, annotations | exact for the compiled configuration (L0) | virtual dispatch targets, DI wiring, reflection, proxies | needs a successful build of both commits (Maven, JDK, private repos) |
| Spring AOT generated bean definitions | which beans exist, which constructor/field gets which bean, after @Profile/@Conditional evaluation | exact for the build-time profile and properties | other profiles or runtime properties; instance-supplier (lambda) beans; beans created by hand-written factories at runtime | build plus `process-aot` per profile set; app must tolerate AOT (it disables runtime @ConditionalOnProperty) |
| Actuator /beans, /mappings (or a test-context dump of RequestMappingHandlerMapping) | live bean set and every HTTP route with its handler method | exact for one running deployment | anything not started in that run; other environments | needs the app to start (DB, brokers) |
| GraalVM reachability analysis / metadata | closed-world reachable methods | sound only modulo complete metadata; metadata from tracing is coverage-limited | dynamic access not recorded | native build is heavy; many apps do not build native |
| Angular ngtsc TCBs (strictTemplates) | each template expression bound to a resolved component member, pipe, directive input | exact (compiler) in strict mode; basic mode skips embedded views | runtime dynamic components, string-based router config computed at runtime | requires a type-checking build of the front end |
| Vue language-core virtual code | template expressions as TS with source maps | exact for what the TS checker resolves | `any`-typed props, dynamic components, global properties | requires node_modules and tsconfig |

- These sources move facts from L3 (Teslon's tokenizer) to L0/L1, which is what Teslon's own council rule asks for ("a SKIP needs an L0/L1 path"; CERTIFICATE doc, "Honest limits"). They also give Teslon something it lacks today: an EXTERNAL fact source, so the checker no longer depends on the same readers as the engine. Today both engine and checker consume the same L3 facts (CERTIFICATE doc, step 1: "different algorithms over the same facts"), so a reader miss is a common-mode failure.
- The design tension: Teslon promises "static reading, offline, no build". A build on the customer's runner is still offline, but it adds failure modes (private registries, JDK versions, long builds). A tiered design is honest: L3 skip (no build) is labelled "rule-checked"; L0/L1 skip (build facts agree) is labelled "compiler-checked".
- Spring AOT's documented restriction is itself a fact Teslon can use: in AOT mode, beans "cannot change at runtime", so the bean graph diff between two commits under the declared profiles is a complete statement of DI-wiring change for that configuration. Teslon currently relies on "a bean switched off by @ConditionalOnProperty here is relied on as off" (CERTIFICATE doc, assumptions); AOT shows why that is only valid per configuration, and gives a way to check each configuration the team deploys.

## Q4. Proving "no behaviour change": what gives a sound "nothing changed" verdict cheaply

### Takeaway
Only one family gives a sound AND cheap "nothing changed" verdict: identity of what the real compiler produces (normalised bytecode / emitted JS), as in trivial compiler equivalence and Ekstazi's smart checksums. It is sound but very incomplete (it proves "same" only when the output is identical). Semantic equivalence provers (regression verification, SymDiff, differential symbolic execution) are sound but undecidable in general, have no production Java/Spring tool, and assume a closed program that framework reflection breaks. Refactoring detectors and AST diffs (RefactoringMiner, GumTree) classify edits; they do NOT prove behaviour preservation, and in Spring apps renames routinely ARE behaviour changes. Measured in this session: Teslon's source-token identity check, which it uses as its "nothing changed" verdict, is not compiler identity and gives a silent wrong answer on a compiler-accepted behaviour change.

### Cited Findings
- Godlin and Strichman, "Regression Verification", DAC 2009, pp. 466-471; journal version STVR 23(3):241-258 (2013): proving equivalence of closely related versions "has the potential of being easier in practice than functional verification, although both problems are undecidable"; easier because no specification is needed, the problem decomposes, and an automatic invariant handles loops/recursion "in most practical cases"; prototype for C. — [Microsoft Research page](https://www.microsoft.com/en-us/research/?p=181920); [Strichman grand-challenge PDF](https://ofers.dds.technion.ac.il/publications/grand-challenge.pdf) [S]
- SymDiff (Lahiri et al., Microsoft Research): differential program verifier at the Boogie level using mutual summaries and product programs; differential assertion checking (FSE 2013) reduces two-version checking to safety checking of a composed program. — [SymDiff project](https://www.microsoft.com/en-us/research/project/symdiff-differential-program-verifier/); [Lahiri slides](https://homes.cs.washington.edu/~akcheung/pnw16/lahiri.pdf) [S]. Person, Dwyer, Elbaum, Pasareanu, "Differential Symbolic Execution", FSE 2008: summarises both versions symbolically and compares summaries to characterise behavioural differences [Mem; citation not confirmed by search].
- Papadakis, Jia, Harman, Le Traon, "Trivial Compiler Equivalence", ICSE 2015: compiling mutants and comparing binaries discards more than 7% of all mutants as equivalent and 21% as duplicates; human checking shows TCE detects about 30% of all equivalent mutants (journal extension by Kintis et al.: about one third in C, about half in Java). — [ICSE 2015 PDF](https://orbilu.uni.lu/bitstream/10993/20289/1/ICSE15.pdf); [journal extension](https://orbilu.uni.lu/bitstream/10993/31623/1/07882714.pdf) [S]. Meaning: compiler identity is sound for "same" but misses most semantically-equal-yet-different code.
- Gligoric, Eloussi, Marinov, "Practical Regression Test Selection with Dynamic File Dependencies" (Ekstazi), ISSTA 2015: compares .class files with "smart checksums (e.g., ignoring debug information)", which reduced selected time (e.g. Ivy 63% to 53%). — [ISSTA 2015 PDF copy](https://typeset.io/pdf/practical-regression-test-selection-with-dynamic-file-28si4g2dlc.pdf) [S]
- Tsantalis, Ketkar, Dig, "RefactoringMiner 2.0", IEEE TSE 48(3) 2022 (online 2020): 99.6% precision, 94% recall at detecting refactorings; later oracle of 12,073 refactorings gives 0.998/0.975. — [GitHub](https://github.com/tsantalis/RefactoringMiner) [S]. It detects that a refactoring happened, not that behaviour is preserved.
- Soares, Gheyi, Massoni, "Automated Behavioral Testing of Refactoring Engines", IEEE TSE 2013: 153,444 transformations by Eclipse JDT, NetBeans and JastAdd refactoring tools produced 57 compilation-error bugs and 63 behavioural-change bugs. — [TSE 2013 PDF](https://microsoft.com/en-us/research/uploads/prod/2020/08/tse12.pdf) [S]. Even IDE-applied "behaviour-preserving" refactorings change behaviour.
- GumTree (Falleri et al., ASE 2014): AST edit scripts; purely syntactic, no semantic claim. [Mem]
- MEASURED HERE [V]: Java translates unicode escapes before lexing (JLS 3.3) [Mem for the JLS reference], so `// note \u000a x = 2;` inside a method is a comment plus a real statement to javac. Commands and output (scratchpad/field/soundness/):
  - `javac A.java && java A` on `int x = 1; // note \u000a x = 2;` then `return x;` printed `2`.
  - java-parser (the lexer Teslon uses, java.ts:1 and tokenize at java.ts:80-92) produced the identical token stream for base and head, so `sameTokens` (java.ts:397-405) returns true.
  - End to end on a copy of fixtures/orderdesk: one line `// rounding note \u000a quantity = quantity * 2;` added to `PricingService.lineTotal`. Truth written first: every area that prices order lines must be TEST. Teslon output: `appEffect: "none"`, "No effect on the running app: 1 file (java)", ledger reason "only comments or layout changed: the code is the same, token for token", test 0, skip 0, unclear 0, confidence "High". The certificate cannot catch it, because Δ is computed from the same tokens ("A comment-only change is not a change", CERTIFICATE doc step 2). This is a silent miss with High confidence. It is adversarial (Trojan-Source class), not a likely honest edit, but it proves the token check is not the compiler oracle it is used as.

### Inferences
- Cheap sound "no change" verdicts available to Teslon, best first: (1) normalised-bytecode identity per class/method from a real `javac` build of both commits (strip LineNumberTable/LocalVariableTable; keep annotations and constant pool; note javac inlines compile-time constants, so compare all classes, not just changed files); (2) tsc/ngc emitted-JS identity per module for front ends (proves the "types are erased" rule instead of asserting it); (3) Teslon's token identity as a fallback only after rejecting any file containing `\u` escapes, bidi/control characters, or unparsable regions. The minimal fix for the measured hole is one line: treat any changed comment containing `\u` as a code change.
- Equivalence provers are not a launch item: no Java/Spring-grade tool, and framework semantics (JSON names, bean names, derived queries, parameter names) sit outside the program text they reason about.
- "It's only a rename" must never be a skip reason in Spring code without a framework-name check: renaming a getter changes JSON, a class name changes the default bean name, a repository method name is a query (Teslon's own gauntlet case u4-04), a parameter name binds requests when compiled with -parameters (u4-06).

## Q5. Static analysis across services and data (REST matching, Kafka, ORM/schema)

### Takeaway
The best published static extractors of microservice dependencies report roughly 85-98% recall on curated open-source apps, i.e. none claims soundness, and all match services by keywords, URL strings and configuration, which breaks on computed URLs, service discovery and gateways. Cross-service and data paths are therefore the area where a SKIP should most often be UNCLEAR unless the link is resolved exactly.

### Cited Findings
- Schneider and Scandariato, "Automatic Extraction of Security-Rich Dataflow Diagrams for Microservice Applications written in Java" (Code2DFD), JSS 2023 (arXiv 2304.12769): keyword search over code and configuration; overall precision 93%, recall 85% on 17 manually curated open-source Java microservice apps. — [arXiv](https://arxiv.org/abs/2304.12769v1) [S]
- "Comparison of Static Analysis Architecture Recovery Tools for Microservice Applications" (arXiv 2412.08352, Dec 2024): Code2DFD best on F1; component precision 0.97, recall 0.98 (missed 5 of 182 components). Component-level, not call- or data-flow-level. — [arXiv](https://arxiv.org/pdf/2412.08352) [S]
- Cerny and colleagues (Prophet, microservice reconstruction, 2020-2023) and MicroDepGraph (Rahman et al., 2019) reconstruct endpoint-to-endpoint calls from source annotations and REST client calls; they report case-study accuracy on benchmarks such as TrainTicket, not soundness. [Mem; not re-checked]
- Maule, Emmerich, Rosenblum (ICSE 2008) schema-change impact with no false negatives on one CMS is in academic_cia_rts.md (Q3 there); not repeated.

### Inferences
- Teslon's cross-service rules (Feign, WebClient, Kafka topics, gateway) are the same keyword/annotation class as Code2DFD. ## Q6. How analyzers are tested for soundness, and an honest judgement of Teslon's "independent checker" and "compiler oracle"

### Takeaway
The field tests analyzer soundness by comparing against an independent semantics (a concrete interpreter, a compiler, dynamic traces) on generated or mutated programs, and builds trust with the de Bruijn criterion: a small trusted checker that validates an untrusted producer's certificate against INDEPENDENT ground truth. Teslon's checker is a second algorithm over the SAME facts; teammates found that it shares file classification, Java facts (without modifiers) and setting readers with the engine, and it certified all four wrong skips the red team found. It is therefore a consistency check (it catches graph-walk bugs in the engine), not a certificate in the translation-validation sense. Its compiler oracle is a genuine independent source, but only for Java behaviour mutants on Teslon's own fixtures.

### Cited Findings
- Cuoq, Monate, Pacalet, Prevosto, Regehr, Yakobowski, Yang, "Testing Static Analyzers with Randomly Generated Programs", NFM 2012: Csmith-generated C programs run concretely and checked against Frama-C's value analysis found many soundness bugs in a mature analyzer. [Mem]
- Klinger, Christakis, Wustholz, "Differentially Testing Soundness and Precision of Program Analyzers", ISSTA 2019: generates program variants with known-reachable assertions and compares analyzers against each other; found soundness and precision issues in mature analyzers (Crab, SeaHorn, CPAchecker, Ultimate and others). — [ISSTA 2019 page](https://conf.researchr.org/details/issta-2019/issta-2019-Technical-Papers/32/Differentially-Testing-Soundness-and-Precision-of-Program-Analyzers) [S for existence; findings Mem]
- Metamorphic / mutation-based testing of analyzers (e.g. Taneja et al. "Testing static analyses for precision and soundness", CGO 2020, LLVM dataflow facts checked by brute-force; Zhang et al. and others for call graphs): semantics-preserving transformations must not change the verdict; semantics-changing ones must. [Mem]
- Translation validation (Pnueli, Siegel, Singerman, TACAS 1998; Necula, PLDI 2000): instead of verifying the compiler, check each run's output against its input with an independent checker. Certifying algorithms (McConnell, Mehlhorn, Naher, Schweitzer, Computer Science Review 2011): an algorithm outputs a witness that a simple checker validates. De Bruijn criterion (Barendregt and Wiedijk): proofs checkable by a small independent kernel. [Mem]. The common requirement: the checker must re-derive from the ORIGINAL input (source/semantics), not from the producer's intermediate facts.
- Teslon CERTIFICATE doc: "The engine walks backward from the change, so the two walks are different algorithms over the same facts"; "Facts come from Teslon's own readers: a tokenizer and parsers, not a compiler"; "Content claims are relied on, not proven". Its soundness test fed truth-reached areas to the checker and certified 0 of 255 (ShopFlow) and 0 of 493 (OrderDesk); the first run certified 61 of 255. [V, /home/user/teslon/research/CERTIFICATE-2026-11-05.md]
- Teslon GAUNTLET doc: oracle built from javac + javap bytecode plus hand-written framework rules (Jackson, @Valid, handlers, events, Feign, Kafka, JPA callbacks); "The oracle is ours too"; blind to reflection, library callbacks, data effects; Java only; fixtures are Teslon's own. [V, /home/user/teslon/research/GAUNTLET-2026-11-05.md]
- This session [V]: the Q4 unicode-escape case is a common-mode failure: reader, engine Δ and checker Δ all used java-parser tokens, so all agreed on a wrong "no effect".

### Inferences (judgement)
| Teslon component | What it proves | What it does not prove | Literature analogue |
|---|---|---|---|
| Independent checker (certify.ts) | the engine's skip is consistent with the extracted facts under a second graph walk; catches engine walk bugs | anything the readers missed or mis-classified (common inputs); content/data effects (relied on, ~43% of impact); framework semantics not in the rules | N-version programming with shared inputs; NOT translation validation (no independent semantics) |
| Checker soundness test (truth areas fed to checker) | on two fixtures, the checker refuses every area the hand truth marks reached | areas the truth author also missed; real-world code | differential testing with a hand oracle; same authors write rules and truth |
| Compiler oracle (javac/javap + oracle.mjs) | for injected behaviour mutants, the bytecode call graph plus framework rules reaches the same areas | front ends, config, data, reflection, library callbacks; oracle rules written by same team | Klinger-style differential testing; mutation-based soundness testing |
| Comment mutants (bytecode-identical) | no false TEST on comment edits | does not test the reverse (a "comment" that is code: Q4) | TCE |

- To make the checker a real certificate it needs at least one input the engine does not share: compiler facts (javac symbols/bytecode, tsc/ngtsc), Spring AOT bean definitions, or runtime traces. The cheapest decoupling: compute Δ in the checker from compiler output identity (normalised bytecode, emitted JS) and file classification from the build (what is on the runtime classpath/bundle), not from Teslon's readers.
- Apply analyzer-testing practice to Teslon itself: (a) metamorphic tests: inject semantics-preserving edits (rename local, reorder imports, reformat) that must not change the verdict, and semantics-changing edits that look harmless (unicode escapes, constant inlining across classes, annotation retention, Lombok/MapStruct generated code, profile-only settings) that must; (b) random program generation is less useful for framework apps than mutation of real apps; (c) red-team PRs written by people who did not write the rules.

## Q7. Statistical evidence and how safety standards qualify verification tools

### Takeaway
Zero observed wrong skips in n independent skip decisions bounds the true rate at about 3/n (95%). Safety standards do not accept testing alone for a tool whose error can let a fault through undetected: they require tool qualification proportional to impact, i.e. a requirements spec for the tool, verification against it, and a defined operational environment. Teslon is a "verification tool that can fail to detect an error" in every standard's taxonomy, the class that needs qualification when its output is relied on without review.

### Cited Findings
- Rule of three and sample sizes: covered in academic_cia_rts.md (Q8). Not repeated. Exact Clopper-Pearson upper bounds for 0 failures, computed here (one-sided 95%: 1-0.05^(1/n); two-sided 95% uses 0.025): to claim below 1% needs n=299 (one-sided) or 368 (two-sided); below 0.1% needs 2,995 / 3,688; below 0.01% needs 29,956 / 36,887 defect-free decisions that are independent and representative. [arithmetic, V]
- Independence caveat: skips from the same PR, same repo or same change kind are correlated; the bound applies per stratum (stack x change kind), and hand fixtures written by the rule authors are not a random sample. [inference]
- DO-330 / DO-178C: tool qualification levels TQL-1 to TQL-5 from software level and three criteria; Criteria 1 = output is part of airborne software and could insert an error; Criteria 2 = automates verification and its output is used to justify eliminating or reducing other verification or development processes; Criteria 3 = could fail to detect an error. Criteria 3 tools are TQL-5 at all levels; Criteria 2 tools are TQL-4 at Level A/B. A tool that justifies SKIPPING tests is Criteria 2. [Mem]
- ISO 26262-8 clause 11: tool impact TI1/TI2 x tool error detection TD1-TD3 gives tool confidence level TCL1-TCL3; TCL2/3 require qualification methods (increased confidence from use, evaluation of the development process, validation of the tool, development per a safety standard), selected by ASIL. A tool that can fail to detect an error with low chance of the error being caught downstream is TI2/TD3 = TCL3. [Mem]
- IEC 61508-3 (7.4.4) classes T1 (no effect on executable), T2 (verification/test tools that may fail to reveal defects), T3 (can directly introduce errors); T2/T3 need specification of behaviour, evidence of validation or proven-in-use. EN 50128 (railway) uses the same T1-T3 classes with T2 evidence requirements. [Mem]
- NIST SATE VI Ockham criteria are an example of empirical soundness evaluation on a test suite (Q1). [S]

### Inferences
- Teslon's skip is a Criteria 2 / TI2 / T2 tool in these taxonomies. If a regulated customer uses SKIP to remove tests, they will need a tool operational requirements document (what Teslon claims, under which assumptions), a validation suite traceable to it, a known-problems list, and evidence of use; Teslon's assumption list, certificate digests and gauntlet are good raw material for this but are not yet organised as a qualification kit.

## Q8. Hybrid options: does runtime evidence close the gaps?

### Takeaway
Runtime evidence (coverage per test or per manual session, production traces) captures exactly what static analysis misses (reflection, DI, proxies, callbacks, real configuration) but only for executions observed, so it is unsound in the other direction. The combination is strong when used as a cross-check: a static SKIP contradicted by a trace (the area's recorded execution touched changed code) is a detectable wrong skip.

### Cited Findings
- Coverage-based test impact analysis (Teamscale, Microsoft TIA, Ekstazi) is covered in academic_cia_rts.md (Q4/Q5). Not repeated.
- Hybrid RTS: Zhang, "Hybrid Regression Test Selection" (HyRTS, ICSE 2018) mixes method- and file-level dynamic dependencies; Legunsen et al. (FSE 2016) found static RTS can be unsafe where reflection is used. [Mem]
- Jelly (PLDI 2024) uses approximate execution to recover edges static analysis misses: recall 75.9% to 88.1% (Q2). [S]
- GraalVM's tracing agent illustrates the limit: dynamic evidence is only as complete as the runs (Q3). [S]
- SeaLights (coverage from manual and automated test sessions, "quality risk" of untested changes) and Drill4J/Drill4 (open-source Java agent collecting per-test coverage including manual sessions) are commercial/open-source implementations; their accuracy is not published independently. [Mem; vendor positioning]
- OpenTelemetry traces give service-to-service and endpoint-to-endpoint edges actually exercised in an environment (span parent/child, http.route), which is the ground truth for Teslon's cross-service graph in that environment. [Mem]

### Inferences
- Best use for Teslon: (1) a "trace contradiction" check: run the team's existing E2E/regression suite (or staging traffic) with a Java agent on base, record method-level coverage per area (screen/API/job); for every SKIP, if the area's recorded execution touched a changed method, the skip is wrong: hold it and report a Teslon bug. This turns every customer run into soundness evidence; (2) a calibration of Teslon's static graph against observed edges (per-run recall, like Sui 2020 and Jelly); (3) not as a replacement: a skip justified only by "no test touched it" is unsafe.
